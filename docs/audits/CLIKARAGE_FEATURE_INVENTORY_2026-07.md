## Lecture

- `COMPLETE` signifie que l'interface, la persistance, les contrôles serveur, les erreurs et les tests nécessaires sont présents.
- `PARTIELLE` signifie qu'un parcours réel existe, mais qu'au moins une composante structurante manque.
- `UI_SEULEMENT` et `BACKEND_SEULEMENT` distinguent une façade d'un socle non exploitable depuis le produit.
- `MOCK_OU_DEMO` désigne un comportement limité au store de démonstration, à une simulation ou à une fixture.
- `BUGGUEE` est réservé à un comportement dont l'implémentation présente une défaillance démontrable.
- Les mentions `Oui` dans les colonnes techniques signifient seulement qu'une couche existe. Le statut tient compte de sa qualité et de sa couverture.
- Les chemins sont relatifs à la racine du dépôt. Aucun test contre Supabase n'a été exécuté pendant cet audit en lecture seule.

## Constats transverses

1. Les migrations produit existent, mais neuf modules sont automatiquement actifs seulement dans les comptes de démonstration et restent désactivés pour un vrai garage tant que leurs variables ne valent pas exactement `true`.
2. Le modèle avancé atelier est sensiblement plus sûr que le modèle legacy, mais le runtime réel avec flags OFF continue d'utiliser le Kanban `repairs` et des mutations Data API trop larges.
3. Les devis constituent le domaine le plus abouti. Ils ne suffisent pas à compléter le parcours atelier, faute d'ordre de réparation, de temps réalisé, de pièces consommées, de paiement et de dossier véhicule unifié.
4. Le commerce de véhicules d'occasion n'est pas une fonctionnalité du produit actuel. L'Edge Function de génération d'annonce est inutilisée et ne doit pas être comptée comme un module.
5. Les tests RLS sont substantiels, mais ils n'empêchent pas le cas forgé où `service_request_messages.request_id` et `garage_id` appartiennent à deux garages différents.
